# 知识画布（Canvas）

> 最后更新：2026-08-23

> 定位：本文描述 mdgo「知识画布」功能的现状实现（后端格式校验管线、canvas 技能、前端 D3 渲染
> 与编辑、端到端数据流、与大纲思维导图技能的分工）。所有符号均以实际代码为准：
> 后端 `tauri/src-tauri/src/core/agent/tools/canvas.rs`，技能
> `tauri/src-tauri/resources/skills/canvas/SKILL.md`，前端 `css_js/modules/canvas.js` 与
> `main.html`。

---

## 1. 一句话架构

**Canvas 是「Agent 可以读写的知识文件格式」**，不是独立数据库、也没有独立的 canvas IPC 命令。
文件以 **JSON Canvas 格式**（顶层只有 `nodes` / `edges`）落在知识库目录内（`.canvas` 扩展名），
由后端校验管线保证落盘内容合法可渲染，由前端 D3 渲染器负责可视化与编辑，由 canvas 技能引导
模型生成/整理画布。

分工边界（v7 架构，代码注释原文语义）：

```text
LLM（经 Skill 引导）负责全部语义与空间：
  理解知识、设计节点/关系、决定层级/坐标/尺寸/连线方向，输出带最终 x/y/width/height 的完整 Canvas

程序只做机器可验证的合法性校验（core/agent/tools/canvas.rs）：
  JSON parse → schema 校验 → ID 唯一化 → edge 引用完整性 → file 路径存在性 → 坐标/尺寸合法性
  ——绝不计算/覆盖坐标，模型写入的 x/y/width/height 原样保留
```

## 2. 后端

### 2.1 位置与定位

- 文件：`tauri/src-tauri/src/core/agent/tools/canvas.rs`（由 `core/agent/tools/mod.rs` 的
  `pub mod canvas;` 挂出）。
- 定位（文件头注释）：**确定性内部模块，非 Agent 工具**，不做任何布局——它是 write 工具写入
  `.canvas` 文件时自动调用的校验管线。

### 2.2 数据模型（与前端 D3 渲染器共用同一 JSON Canvas 格式）

```rust
pub struct CanvasNode {
    pub id: String,
    #[serde(rename = "type", default = "default_node_type")] pub ty: String, // 缺省 "text"
    pub x: f64, pub y: f64, pub width: f64, pub height: f64,   // 模型负责布局，系统只校验不重算
    pub text: Option<String>,
    pub file: Option<String>,     // file / image 节点绑定知识库文件
    pub url: Option<String>,
    pub code: Option<String>,
    #[serde(rename = "isRoot", ...)] pub is_root: Option<bool>, // 主题中心标记（camelCase）
}
pub struct CanvasEdge {
    pub id: String,                                        // 缺失/重复时自动补唯一 id
    #[serde(rename = "fromNode")] pub from_node: String,
    #[serde(rename = "toNode")]   pub to_node: String,
    pub label: Option<String>,
    #[serde(rename = "fromSide", ...)] pub from_side: Option<String>, // right/left/top/bottom
    #[serde(rename = "toSide",   ...)] pub to_side: Option<String>,
}
pub struct CanvasFile { pub nodes: Vec<CanvasNode>, pub edges: Vec<CanvasEdge> }
```

节点类型仅限 `text` / `file` / `image` / `url` / `code`（v8 起旧文件的 `link` / `bookmark`
归一化为 `url`；无 `group` / `node` 类型——分组通过空间分区表达）。

### 2.3 校验管线（`validate_canvas_json(content, dir) -> Result<String, String>`）

```text
1. serde_json 解析（失败 → "无效的 JSON Canvas 格式: ..."）
2. nodes 为空 → 拒绝（"画布无节点"）
3. 类型归一化：link / bookmark → url
4. sanitize_ids：节点 id 重编号 n1..nN 并同步更新边引用；
   过滤引用不存在节点的悬空边；为缺失/重复的边 id 补唯一 id（e{seq}）
5. degrade_missing_file_nodes：file/image 节点引用的文件在知识库根目录不存在
   → 降级为 text 节点并清空 file（防模型编造路径），返回降级数量
6. validate_geometry：width/height 必须 > 0 且有限；x/y 必须是有限数
   （防 NaN/Infinity 污染画布坐标）；不做任何位置计算或重排
7. serde_json::to_string_pretty 原样序列化（坐标/尺寸/isRoot/fromSide/toSide 全保留）
```

任一步失败返回明确错误（write 拒绝写入），保证落盘的 `.canvas` 合法可渲染。
回归基线：单测引用 `docs/canvas-benchmark-cases/` 下的固定 `.canvas` 用例，验证「坐标原样
保留不被改写」（该目录缺失时测试自动跳过，不硬依赖 docs 资产）。

### 2.4 触发路径：write 工具自动校验

`core/agent/tools/mod.rs::write_file`：

```rust
// Canvas 格式自动处理：.canvas 内容先经确定性校验/规整，再落盘
let effective = if rel_path.ends_with(".canvas") {
    canvas::validate_canvas_json(content, &cfg.dir_path)?
} else {
    content.to_string()
};
```

即：Agent（或任何调用方）用 `write` 工具写入 `xxx.canvas` 时，内容自动过校验管线，失败即拒绝
写入；校验通过后原样落盘。`.canvas` 的读取没有专门逻辑——走通用 `read` 工具。

### 2.5 存储与索引

- **存储**：磁盘上的 `.canvas` JSON 文件（知识库目录内，建议 `canvas/` 目录），**非 SQLite**。
- **检索**：`.canvas` **不在**知识库索引白名单
  `core/db/utils.rs::KB_SUPPORTED_EXTS`（`["md","txt","pdf","docx",...,"opml","mm"]`，
  不含 `canvas`）——因此 `kb_search` / 混合检索**不会**索引 `.canvas` 文件；模型读取画布内容
  必须显式用 `read` 工具（"回答画布相关问题：用 read 读取 .canvas，不凭记忆编造"）。

### 2.6 canvas 技能（resources/skills/canvas/SKILL.md）

front matter：`id: canvas`、`scope: system`、`name: 知识画布（Canvas）`、`priority: 45`、
`version: 10`、`tools: [kb_search, read, write]`、
`triggers: [canvas, 画布, 知识画布, 思维画布, 整理画布, 生成画布, 知识梳理, 管理我的知识, 画布整理]`。

核心内容（与后端校验一一对应）：

- **模型负责完整布局**：节点创建/类型/内容/层级/分组、x/y/width/height、edges 方向、
  fromSide/toSide、整体空间；程序只做格式/路径/写入校验，禁止重算坐标。
- **格式规范**：顶层只有 `nodes`/`edges`；节点 type 仅 `text/file/image/url/code`；
  `isRoot` 最多一个；边 `fromNode/toNode` 必须引用存在的节点；height 最小 80。
- **输出硬性要求**：纯 JSON、不加 ```json 围栏、不发明 `layout`/`groupId` 等字段、
  文本按 JSON 标准转义；内容不合法写入被拒，需按返回原因修正后重写。
- **工作流**：创建（先 kb_search 检索真实资料 → 分析结构 → 设计布局 → write 写入 .canvas）；
  整理（read 读取 → 分析节点/边/空间 → write 覆盖）；回答画布问题（read 读取后回答）。
- **边界**：简单列表用 Markdown，结构化大纲/思维导图（.opml/.mm）用 outline-mindmap，
  图表代码用 mermaid（见 §5）。

## 3. 前端

### 3.1 模块与单例

- 渲染/编辑逻辑集中在 `css_js/modules/canvas.js` 的 **`CanvasLess` 类**。
- **`_canvasObject` 单例**定义在 `main.html`（`let _canvasObject = null`）：

```js
async function renderCanvasFile(text, contentDiv, showSaveBtn = false, _canvasData = null) {
    _canvasObject = new CanvasLess();
    await _canvasObject.renderCanvas(text, contentDiv, showSaveBtn, _canvasData);
}
async function cleanupCanvasState(cleanDom = false) {
    if (_canvasObject) await _canvasObject.cleanupCanvasState(cleanDom);
    _canvasObject = null;
}
```

- `canvas.js` 顶部还导出两个全局包装函数，供 `main.html` 的按钮 onClick 调用：
  `editCanvasNodeContent(e, btn)` → `_canvasObject.editNodeContent(...)`、
  `saveCanvasNodeContent(e, btn)` → `_canvasObject.saveNodeContent(...)`。
- 打开/新建入口：`main.html` 打开 `.canvas` 文件（`fileName.endsWith('.canvas')`）→
  `renderCanvasFile(await getFileText(), contentMain)`；`openCanvasFile(data)` 新建空画布
  （`untitled.canvas`，demo/新文件入口）。

### 3.2 渲染（renderCanvas）

`CanvasLess.renderCanvas(text, contentDiv, showSaveBtn, _canvasData, isChildCanvas)`：

1. `JSON.parse(text)`（失败显示"无效的 JSON Canvas 格式"错误面板）；
2. 建立 SVG：`.canvas-container` + `.canvas-svg`，d3 选 `g.canvas-group`；添加箭头 marker
   （`#arrowhead` 默认 + `#arrowhead-hover` 悬停变蓝）；
3. `initCanvasZoom`（d3 zoom/pan）；空白点击关闭节点面板 + `fitCanvasToContent`
   （以实际渲染内容 bbox 居中，而非仅数据坐标）；
4. `renderCanvasEdges(edges, g, ...)`（`calculateEdgePath` 使用 fromSide/toSide）；
5. `renderCanvasNodes(nodes, g, ...)`——按节点类型渲染：text（Markdown 预览）、file
   （嵌入文件内容预览）、image（并发受限加载）、url、code；根节点 `isRoot` 高亮；
6. 主画布追加底部工具栏与保存控件；`setTimeout(fitFn, 100)` 自适应缩放。

子画布（`isChildCanvas=true`，如 `embedNodeCanvas`）：只读内嵌，一次性把 `<g>` 的 bbox 写入
svg viewBox + `preserveAspectRatio="xMidYMid meet"`，容器 CSS 100% 接管自适应；递归处理嵌套
子画布。

### 3.3 图片并发加载（_CANVAS_IMG_CONCURRENCY = 4）

```js
const _CANVAS_IMG_CONCURRENCY = 4;   // Canvas 图片节点加载并发限制（避免 20 张大图同时解码导致 CPU 飙升）
```

- `_canvasImgQueue` 任务队列 + `_canvasImgInFlight` 计数：`_canvasImgEnqueue(fn)` 入队，
  `_canvasImgProcessQueue()` 在 `inFlight < 4` 时循环出队执行；
- `embedNodeImage`：`getEmbedNodeFileHandleByPath` → `getFile` → `URL.createObjectURL(blob)` →
  注入 `<img>`；blob URL 同时记录到实例级 `_canvasObjectUrls`（重渲染只撤销自己的，避免误撤销
  其他实例/父画布的图片）与全局 `currentObjectUrls`（视图销毁统一清理）。

### 3.4 节点内容与 Markdown/Obsidian 语法衔接

- 节点文本渲染统一走 **`markedParse(parseObsidianToHTML(previewText))`**：
  `parseObsidianToHTML` 把 Obsidian 语法（`[[wikilink]]`、`#tag` 等）转为 HTML，再交 `markedParse`
  （marked 库，项目全局）渲染为 `.markdown-body`；渲染后 `postProcessMarkdown` 做链接/图片等
  后处理。file 节点预览同样走 `markedParse(parseObsidianToHTML(bodyText))`。
- **编辑**（`editNodeContent`）：右侧面板 `#node-content-panel` 进入编辑模式——file 节点编辑
  文件内容（标题 `📝 编辑文件: {basename}`），text 节点编辑节点文本；经
  `initMonacoEditor().then(...)` 创建 Monaco 编辑器（`createMonacoEditor(editorInner, {language:
  'markdown'})`）。
- **保存**（`saveNodeContent`）：`currentNodeEditor.getValue()` → 与原始内容比对：
  - 未变化 → 直接渲染预览；
  - file 节点 → `saveFileNodeContent(filePath, newText)`（`getEmbedNodeFileHandleByPath` +
    `writeFileHandle`，写回**文件本身**）；
  - text 节点 → `nodeData.text = newText` + `saveNodeText(nodeId, newText)`（写回 `.canvas`
    文件，见下）；
  - 保存成功后 `renderPreviewPanel`（markedParse 预览）→ `reloadCanvasData()` 重读文件重渲染。
- 面板关闭（`closeNodeContentPanel`）：有未保存内容时同样自动保存（file 节点写文件 / text 节点
  写节点文本）。

### 3.5 保存回文件（canvasSave / saveNodeText / saveNodesToFile）

```js
async canvasSave() {
    const content = JSON.stringify({ nodes: data.nodes, edges: data.edges });
    if (currentFileHandle) {
        // 500ms 防抖 + enqueueFileAtomic 原子写队列（每文件一条串行链）
        await enqueueFileAtomic(fileHandle, async () => { await _writeToFileHandle(fileHandle, content); ... });
    } else {
        await showSaveModal({ title: '保存canvas画布文件', getDefaultFileName: () => 'untitled.canvas',
                              getContent: () => content, onSave: doSaveToFolder });
    }
}
```

- 读写句柄：浏览器 **File System Access API**（`main.html` 的 `getFileContent(fileHandle)` /
  `_writeToFileHandle(fileHandle, content)`，创建可写流 → 写入 → 关闭，异常 abort）；
  `enqueueFileAtomic` = `enqueueFileWrite`（同一文件句柄的写操作串行排队，防并发覆盖）。
- `saveNodeText`：重读 `.canvas` 文件 → 定位节点改 `text` → `JSON.stringify` 整体写回。
- `saveNodesToFile` / `saveEdgesToFile`：节点/边编辑（增删节点、拖拽改坐标等）后的整体写回；
  新画布无文件句柄时仅置 `canvasData._dirty` 供后续保存感知。
- 快捷键：`Ctrl/Cmd + S` → `canvasSave()`；`Esc` 取消连线模式。

### 3.6 编辑交互

- 节点：单击选中、拖拽移动（更新坐标 → 保存）、拖拽边角改尺寸；四边连接点
  （`.canvas-connector-dot`）拖出连线（`connectingFrom` 状态 + `fromSide` 锚定）。
- 底部工具栏（`#canvas-bottom-toolbar`）：新建节点类型（text / image / file）+ 删除选中节点
  （`canvasDeleteNode`：从 `canvasData` 删节点与关联边 → 保存 → 增量删 DOM）；文件选择模态框
  `showFileSelectModal`（image 显示文件名列表 / file 显示图标列表）。
- 节点内嵌资源：file 节点可内嵌 `.canvas`（子画布）、SVG、mermaid（`embedNodeMmd`）、
  Excalidraw、图片（`embedNodeImage`）等。
- 清理：`cleanupCanvasState(cleanDom)` 释放 d3 zoom 监听、节点面板、图片 blob URL、Esc 监听、
  保存队列，置空 `_canvasObject`。

## 4. 数据流（端到端）

```text
┌─ 用户侧（前端）────────────────────────────────────────────────────┐
│ 打开 .canvas 文件 → renderCanvasFile(getFileText())                │
│   → CanvasLess.renderCanvas：JSON.parse → D3 SVG 渲染 nodes/edges  │
│ 编辑节点 → saveNodeContent → saveNodeText / saveFileNodeContent     │
│   → enqueueFileAtomic → _writeToFileHandle（File System Access API）│
│ 画布级保存 canvasSave（Ctrl+S）→ 同上原子写队列                     │
└────────────────────────────────────────────────────────────────────┘
┌─ Agent 侧（LLM + 工具）────────────────────────────────────────────┐
│ 用户要求"生成/整理画布" → 激活 canvas 技能（activate_skill）         │
│   → SKILL.md 引导：检索（kb_search）→ 设计布局 → 输出纯 JSON         │
│   → write 工具写 xxx.canvas                                        │
│     └─ write_file 检测 .canvas 扩展名 → validate_canvas_json 校验   │
│        （ID 唯一化 / 悬空边过滤 / 路径降级 / 几何校验）→ 原样落盘     │
│ 回答画布问题 → read 工具读取 .canvas（内容含坐标）→ 分析回答          │
│ 整理画布 → read 读取 → 分析节点/边/空间 → write 覆盖（同校验）       │
└────────────────────────────────────────────────────────────────────┘
```

要点：

- **没有 canvas 专用的 IPC 命令**：`lib.rs` 的 invoke_handler 中不存在
  `canvas_read` / `canvas_write` / `canvas_list` 之类的命令（已核实）；后端读写全部走通用
  `read` / `write` 工具，前端读写走浏览器 File System Access API 文件句柄。
- **Agent 不经"canvaskb 检索"**：`.canvas` 不在 `KB_SUPPORTED_EXTS`，知识库混合检索不索引
  画布；模型获取画布内容唯一途径是 `read` 工具（技能明确要求"不凭记忆编造"）。
- **两处校验语义一致**：后端 `validate_canvas_json` 与前端 `renderCanvasFile` 的
  `JSON.parse` + 错误面板共用同一 JSON Canvas 格式契约；前端编辑保存不经后端校验（浏览器
  端直接写文件），后端校验是 Agent 写入路径的守门员。

## 5. 使用场景与技能分工

### 5.1 知识画布技能（canvas）

- **创建**：把主题/资料整理为二维知识空间（节点 = 知识对象、边 = 知识关系、位置 = 语义关系的
  空间表达、方向 = 关系方向、距离 = 关联强弱、分组 = 知识领域）；写 `.canvas`（建议 `canvas/`
  目录，文件名优先中文）。
- **整理**：分析/合并/删除节点、补关系、重新设计坐标以改善可读性。
- **回答画布相关问题**：read 后回答；也可用于寻找孤立节点、知识缺口、关系错误（triggers）。

### 5.2 与大纲思维导图技能（outline-mindmap）的关系

两者是**不同格式、不同技能、互不耦合**的并行能力（分工边界在两个 SKILL.md 中互为镜像）：

| 维度 | 知识画布（canvas） | 大纲思维导图（outline-mindmap） |
|---|---|---|
| 文件格式 | `.canvas`（JSON Canvas，`{nodes, edges}`，自由二维空间） | `.opml`（大纲）/ `.mm`（FreeMind 思维导图） |
| 数据结构 | 节点 + 边 + 模型坐标（空间 = 知识表达） | 统一**树模型**（树 ↔ .opml ↔ .mm 映射，jsMind 渲染） |
| 布局责任 | 模型全权负责（系统只校验） | 树层级结构（系统渲染树） |
| 技能 ID | `canvas`（v10） | `outline-mindmap`（v3，commit `124dfb4` "实现技能正文内存直读，优化大纲思维导图技能" 更新过其 SKILL.md 与 references/） |
| 边界声明 | canvas SKILL.md："结构化大纲/思维导图文件（.opml/.mm）使用 outline-mindmap；图表代码使用 mermaid" | outline-mindmap SKILL.md："不处理 mermaid 图表、看板、日程、普通笔记写作等" |

参考 commit（git log 核对的演进线索，行为以当前代码为准）：

- `2d84342` feat: 新增知识画布功能与配套优化
- `cc5cac5` feat(canvas): 新增 10 个 benchmark 用例并完善画布布局校验与测试
- `124dfb4` feat: 实现技能正文内存直读，优化大纲思维导图技能与构建配置

### 5.3 其他触点

- `open-ui` 工具的 `page` 枚举含 `canvas`（跳转打开画布页面视图，`loop_tools.rs` 的 open-ui
  schema 中 26 个页面之一）。
- `DOC_EXT_SET`（main.html）含 `canvas`：画布文件视为可打开/可渲染文本类型。
