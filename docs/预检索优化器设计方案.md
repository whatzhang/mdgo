# 预检索优化器（Pre-Retrieval Optimizer）设计方案

> **状态：方案已全量落地（P0/P1/P2）**——P0-1~P0-6、P1-A（`query_sources` / `agreement_bonus`）、
> P1-B（`hybrid_recall` 拆分 + 池级精排 `rerank_pool`）、P2 符号实体发现（`commands/llm.rs` 预检索 entity 变体）均已实现。
> `cargo check --all-targets` 通过、`cargo test --lib` 321 通过。
>
> 本文档保留为**方案设计基线**（为什么这么设计、四层边界、fail-open 纪律、裁决表）；
> 实施细节、文件映射与行为变化见 [预检索优化器实施归档.md](./预检索优化器实施归档.md)（以代码为准，
> 与方案的差异——时限 10s→5s、重试 1→2 次、P2 符号实体发现提前落地等——均已标注）。

> 定位：把现有「输入语义扩展（固定 3 条 Query 改写）」收敛为**一次性、低延迟、结构化、可失败降级的预检索优化器**。
>
> 一句话工程目标（替代"超过主流 Agent"）：
> **让 Agent 第一次检索就拿到更高覆盖率、更低冗余、更高证据一致性的上下文，同时不增加一个新的 Agent Loop。**
>
> 前置阅读：检索 V2 架构评估（§十三 Query Rewrite 已达成）与《混合检索技术设计》（检索管线结构）。

## 1. 最终架构：四层边界

```
┌─────────────────────────────────────────────┐
│                Agent Layer                  │
│  推理 / 工具调用 / 多轮                      │
│  kb_search / code_lookup / 自主补检索        │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│          Pre-Retrieval Intelligence         │
│  规则门 should_expand                        │
│       ↓                                     │
│  一次性 LLM Expansion（0~2 条）              │
│       ↓                                     │
│  Embedding 去重 + 格式校验                   │
│       ↓  （全部 fail-open）                 │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│             Retrieval Engine                │
│  向量 + BM25 + 符号 多路召回                 │
│       ↓                                     │
│  RRF 融合                                   │
│       ↓                                     │
│  Candidate Pool（跨查询合并）                │
│       ↓                                     │
│  Pool Rerank（按来源查询计分 + max）         │
│       ↓                                     │
│  Diversity / Context                        │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              Knowledge Index                │
│  向量 / BM25 / 符号 / 元数据                │
└─────────────────────────────────────────────┘
```

**边界纪律**（违反即退回重做）：
- 预检索层每请求至多 **1 次** LLM 调用；"不够就再搜"归 Agent 层；
- 检索路径（`hybrid_search` 内部、kb_search 工具）**零 LLM 开销**（`query_plan.rs` 既有原则）；
- 任何 LLM 输出/扩展失败都 fail-open 到"原始查询单跑"。

## 2. 模块收敛：Query Expansion = 一个很小的模块

```
Query Expansion
│
├── should_expand(query, plan)      ← 规则（零 LLM）
├── LLM 生成 0~2 条                  ← 唯一 LLM（一次调用）
├── 格式校验                        ← deterministic（复用 JSON Schema 校验）
├── embedding 去重                  ← deterministic（cosine ≥ 0.92）
└── fail-open                       ← deterministic（timeout/cancel/解析失败→原始查询）
```

**不做**：Planning / Decomposition / Feedback / Replanning / Knowledge Graph（这些职责分属 Agent 层或独立立项）。

## 3. P0：Phase 1 详细设计（先落地）—— 全部已实现

### P0-1 原始检索与扩展并行 ✅ 已实现

**现状（改造前）**：`commands/llm.rs` Stage 1 `expand_queries` 串行 await，Stage 2 才开始检索——LLM 延迟阻塞首答。

**改造（已实现）**：

```rust
// Stage 1+2 重构（commands/llm.rs）
let original_fut = async {
    // 原始查询立即 embedding（单独 spawn_blocking）→ hybrid_recall
    search_single(&state, &dir_path, &query, effective_top_k).await
};
let expansion_fut = async {
    // LLM 扩展带独立总时限（见 P0-5）
    tokio::time::timeout(
        Duration::from_secs(QUERY_EXPANSION_TIMEOUT_SECS),
        llm.expand_queries(&query, &messages, cancel.clone()),
    )
    .await
    .unwrap_or_default()          // 超时 → 空 Vec → fail-open
};
let (original_hits, expanded) = tokio::join!(original_fut, expansion_fut);

// 扩展到达后：批量 embedding（P0-3）→ 并行检索（buffer_unordered(2)）→ merge all_hits
```

- 取消语义：两路共用同一 `cancel`（扩展内部 `retry_loop` 已响应取消；检索路沿用 `take_until(cancel_fut)` 模式）；join 后保留 `cancel.is_cancelled()` 检查点。
- 扩展为空/失败 → 只提交原始命中，**原聚合路径不变**。
- **现状说明**：原始检索与扩展确实并行（原始检索不再被扩展阻塞）；但扩展调用本身的等待仍在首答关键路径上（join 后流水线才进入下一阶段）——审查 L28 已指出 5s 时限与重试 2 次不匹配的问题，属排期调优项。

### P0-2 自适应扩展：规则决定"要不要"，LLM 决定"几条" ✅ 已实现

**规则门 `should_expand`**（`core/search/query_plan.rs`，零 LLM）：

```rust
pub fn should_expand(query: &str, plan: &QueryPlan) -> bool {
    let q = query.trim();
    if q.is_empty() { return false; }
    if q.chars().count() < 8 { return false; }            // 超短查询
    if plan.intent == RetrievalIntent::Code && !plan.symbols.is_empty() { return false; } // 纯符号/精确代码检索
    if is_file_path_like(q) { return false; }             // main.rs / Cargo.toml / a/b.ts
    true
}
```

- `is_file_path_like`：单 token 且含扩展名，或含路径分隔符。
- 判定"不要扩展"的查询（`Redis`、`main.rs`、`UserService`）直接走原始检索，省一次 LLM。

**LLM 侧**：prompt 输出 0~2 条，不足 2 条不凑数；上限常量（`core/agent/limits.rs`，已实现）：

```rust
pub const MAX_EXPANDED_QUERIES: usize = 2;   // 扩展上限
pub const MAX_TOTAL_QUERIES: usize = 3;      // 原始 + 扩展
```

**原因**：每个查询后面是 嵌入+BM25+向量+符号+RRF+精排+聚簇 全管线，3 条扩展 = 4 次昂贵检索；2+1 是延迟/收益的商用平衡点。

### P0-3 Batch Embedding（含修正） ✅ 已实现

- `core/db/utils.rs`：

```rust
pub fn call_embedding_queries(texts: &[&str]) -> Result<Vec<Vec<f32>>, String> {
    let prefixed: Vec<String> = texts.iter()
        .map(|t| format!("{}{}", BGE_QUERY_INSTRUCTION, t))
        .collect();
    let refs: Vec<&str> = prefixed.iter().map(|s| s.as_str()).collect();
    call_embedding(&refs, None)          // 内部 BATCH_SIZE=128 批量推理
}
```

- **修正（已按此实现）**：不要 `[original, q1, q2]` 一批——那会让原始查询 embedding 等 LLM 返回，破坏 P0-1。正确组合：
  - 原始查询：**立即**单独 embedding + 检索（不等 LLM）；
  - 扩展查询（0~2 条）：LLM 返回后**合一批** `call_embedding_queries`，一次 `spawn_blocking`。

### P0-4 Embedding 去重（替换 char Jaccard） ✅ 已实现

- 去重时机：**向量化之后**（候选反正都要 embedding，零额外推理）。
- 阈值 `QUERY_DEDUP_SIMILARITY = 0.92`，`core/search/query_plan.rs::dedup_expanded_queries(original_vec, vectors, threshold, max_keep)`：
  - 与原始查询向量 cosine ≥ 阈值 → 丢弃（无增量价值）；
  - 与已保留扩展向量 cosine ≥ 阈值 → 丢弃；
  - 返回保留下标，保持原顺序，最多 `max_keep` 个。
- 保留"新增实体的查询不算重复"语义（`Redisson RLock` vs `Redis 分布式锁` 语义近但实体增益大）——是否含新实体由调用方结合 kind/符号判定，P2 符号实体发现已实现（见 §5）。
- 未来按 kind 分域调参（Keyword 0.90 / Semantic 0.94 / Entity 0.96）留参数入口，Phase 1 未实现。

### P0-5 独立总时限（用户修正采纳，常量已按现状更新） ✅ 已实现

```rust
// core/agent/limits.rs（现状）
pub const QUERY_EXPANSION_TIMEOUT_SECS: u64 = 5;    // 原方案 10s → 收窄到 5s（慢端点少等 5s）
pub const QUERY_EXPANSION_RETRY_MAX: usize = 2;    // 原方案 1 → 2（扩展输出短、成本低，对齐主流重试耐心）
```

**实现要点**：
- 用 `tokio::time::timeout` 包裹**整个扩展调用**（含重试），而非只改 HTTP 客户端超时；
- 超时/取消/LLM 错误/无效 JSON → 空 Vec → fail-open；并行化后原始检索已在进行。

### P0-6 fail-open 全覆盖（现状保留 + 补位） ✅ 已实现

| 失败点 | 降级 |
|---|---|
| timeout / cancel | 空 Vec → 原始查询 |
| LLM error / 重试耗尽 | 空 Vec → 原始查询 |
| 无效 JSON / 解析失败 | 空 Vec → 原始查询 |
| embedding 失败（批量） | 该批跳过；原始查询命中已就绪 |
| 单路检索失败 | 现有逻辑：向量失败跳该路，BM25 失败降纯向量（`hybrid_recall`） |

**铁律：扩展模块任何失败不得导致整个 RAG 失败。**

## 4. P1：Phase 2 详细设计 —— 全部已实现

### P1-A `SearchHit.query_sources` + Cross-Query Agreement ✅ 已实现

**数据结构**（`core/db/lance.rs`）：

```rust
#[derive(Debug, Clone, Copy, Serialize, Deserialize, PartialEq)]
pub enum QuerySource { Original, Expanded(u8) }   // u8 = 扩展序号

pub struct SearchHit {
    // ...现有字段
    #[serde(default)]
    pub query_sources: Vec<QuerySource>,
}
```

**写入路径**（已实现）：`commands/llm.rs` 预检索对每路命中打标（Original / Expanded(n)）；`rerank_pool` 池级去重时合并来源（保留最高分命中的来源集）。

**Agreement 不粗暴加分（用户修正采纳）——与查询多样性联动**（`core/agent/mod.rs::agreement_bonus`）：

```rust
// 常量（limits.rs）：QUERY_DIVERSITY_THRESHOLD = 0.85；AGREEMENT_BONUS_WEIGHT = 0.05
// 文档代表分 = 最佳 chunk 分 + agreement_bonus（clamp ≤ 1.0）
// agreement_bonus = 来源查询对 cosine < 0.85 的对数 × 0.05 —— 仅影响排序，不改变通过/拒绝
```

- 三个相似查询命中 A（`Redis 分布式锁` / `Redis 分布式锁实现` / `Redis 分布式锁代码`）→ 多样性低 → 不加分，避免**虚假共识**；
- 三个异构查询命中 A（`Redis 分布式锁` / `Redisson RLock` / `Redis Lua 原子锁`）→ 多样性高 → 加分，证据可靠。
- **零额外成本**：查询向量 P0 已算，pairwise cosine 直接用。

**调试价值**：`rag:done` 引用来源可展示"被几个查询命中"。

### P1-B Candidate Pool 统一 Rerank（含修正） ✅ 已实现

**现状（改造前）**：`hybrid_search` 内部每查询一次精排，3 个查询 = 3 次 cross-encoder 推理。

**修正后设计**（cross-encoder 必须带查询）：

1. **拆分 `hybrid_search`**（已实现）：新增 `hybrid_recall(dir, vec, query, top_k) -> Vec<SearchHit>`（召回 + RRF + 向量噪声过滤，**不含精排**）；`hybrid_search` = `hybrid_recall` + 精排（Top-50 截断）+ `finalize_hits`（保持 kb_search 工具行为不变）。
2. **池级合并**（`commands/llm.rs`，已实现）：多查询的 `hybrid_recall` 结果按 `doc_name + chunk_index` 去重合并 → Candidate Pool。
3. **池级精排**（`core/indexer.rs::rerank_pool`，已实现）：对每个候选，**按命中它的来源查询**分别 `rerank(query_i, [candidate], min_score)` 取 max（跨查询重复 chunk 只推理一次）；精排失败 → 回退池级 RRF 排序。
4. 无来源标注的候选原样保留（不参与精排，防丢失）；统一按 `min_score`（sigmoid 域）阈值过滤。

**收益**：跨查询重复 chunk 的精排调用数从 `Σ每查询候选数` 降到 `去重后候选数`；`rerank_min_score` 在统一 sigmoid 域裁决一次；为 P1-A agreement 特征提供统一分数域。

> 说明：用户方案"ONE Rerank"在 cross-encoder 语义下不成立（精排必须知道 query），本设计是其**可行等价物**——成本节省来自池级去重而非单次调用。
> 已知限制（审查 M16）：`rerank_pool` 未套用 50 条精排截断（每路 40-80 条 × 最多 5 查询全量精排），与单查询路径不一致，排期修复。

## 8. 风险与护栏（增量）——现状复核

|---|---|---|
| 并行后 embedding/rerank CPU 并发叠加 | 原始 embedding 单独 + 扩展批量一次；池级精排仍走 `spawn_blocking`，`GLOBAL_SESSION` Mutex 天然串行 | ✅ 保持 |

| 功能膨胀回"小 Agent" | 硬性检查：预检索层 LLM 调用次数 ≤1/请求；无循环、无状态、无持久化 | ✅ 保持 |

## 10. 结论

本方案与现有 mdgo 架构完全对齐：**预检索层一次性、确定性、可降级；Agent 层保持唯一的自适应循环**。落地顺序 P0（并行 + 0~2 自适应 + 批量 embedding + 去重 + 5s 时限）→ P1（来源追踪 + 池级精排 + 一致性加分）→ P2（符号实体发现）**已全部完成**；结构检索 / 别名图 / kind 路由仍为后续排期。

护城河不是"再堆一个 LLM Planner"，而是把已有的 `RuleQueryPlanner + Vector + BM25 + Symbol + RRF + Reranker + Diversity + Context Window + Agent Tool Loop` 通过**一次性 Query Expansion + Candidate Pool Fusion** 正确组合——本方案正是这一组合的设计基线。
