# 预检索优化器实施归档

最后更新：2026-08-23

> **实施归档**：本文记录预检索优化器（Pre-Retrieval Optimizer）的**落地事实**。
> 对应设计方案：《预检索优化器设计方案.md》（`docs/` 下，保留为方案基线）；
> 本归档以代码为准（`cargo test --lib` 通过，HEAD = edab77e + RAG P0 工作区改动），
> 与方案的差异（时限 10s→5s、重试 1 次（原实现 2 次，🟠 L28 已修正）、P2 提前落地等）均已标注。

## 1. 架构（四层边界）

```text
┌─────────────────────────────────────────────┐
│                Agent Layer                  │
│  推理 / 工具调用 / 多轮                      │
│  kb_search / code_lookup / 自主补检索        │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│          Pre-Retrieval Intelligence         │
│  规则门 should_expand（零 LLM）              │
│       ↓                                     │
│  一次性 LLM Expansion（0~2 条，一次调用）     │
│       ↓                                     │
│  Embedding 去重（cosine 0.92）               │
│       ↓  （任何失败 fail-open → 仅原始查询）  │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│             Retrieval Engine                │
│  hybrid_recall（向量+BM25+符号 → RRF）        │
│       ↓                                     │
│  候选池合并（来源打标）→ rerank_pool 池级精排  │
│       ↓                                     │
│  finalize_hits（多样性聚簇 + 上下文窗口）     │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              Knowledge Index                │
│  向量 / BM25 / 符号 / 元数据                │
└─────────────────────────────────────────────┘
```

**边界纪律**（与方案一致，代码已落实）：

- 预检索层每请求至多 **1 次** LLM 调用（`expand_queries`）；"不够就再搜"归 Agent 层；
- 检索路径零 LLM 开销（`query_plan.rs` 规则路由原则未变）；
- 任何 LLM 输出/扩展失败都 fail-open 到"原始查询单跑"（铁律：扩展模块任何失败不得导致整个 RAG 失败）。

## 2. P0 落地清单（已实现）

### 2.1 规则门 `should_expand`（`core/search/query_plan.rs:280-295`）

跳过场景（零 LLM 开销）：

| 场景 | 判定 |
|---|---|
| 空查询 | `q.trim().is_empty()` |
| 超短查询 | `q.chars().count() < 8` |
| 纯符号/精确代码检索 | `plan.intent == Code && !plan.symbols.is_empty()`（符号路由已覆盖） |
| 文件名/路径类查询 | `is_file_path_like`：含 `/` 或 `\`，或单 token 带 ≤5 位字母数字扩展名 |

### 2.2 LLM 扩展 0~2 条（`services/llm.rs::expand_queries`）

- 输出 `{"queries": [{"text", "kind": "keyword|entity|semantic"}]}`，JSON 解析失败回退按行解析（旧格式，全部标 Keyword）；
- 数量自适应：LLM 输出 0~2 条，**不足时不得凑数**；系统侧上限 `MAX_EXPANDED_QUERIES = 2`；
- 轻量清洗：字节长度 ≤5 过滤 + 精确去重 + 数量上限（语义去重由调用方在向量化后做）；
- 参数：`temperature = 0.2`、`max_tokens = 1024`、非流式；
- **与方案的差异**：方案写"重试降 1 次"，实现一度为 `QUERY_EXPANSION_RETRY_MAX = 2`，
  已随 🟠 L28 修复改回 **1 次**（5s 总时限容纳不下第 2 次重试，见常量表）。

### 2.3 原始查询与扩展并行（`commands/llm.rs:1130-1205`）

```text
原始查询：立即 spawn_blocking(call_embedding_query) → hybrid_recall   ┐
                                                                      ├─ tokio::join!
LLM 扩展：tokio::time::timeout(QUERY_EXPANSION_TIMEOUT_SECS,          ┘
          expand_queries)（超时/失败 → 空 → fail-open）
```

- 扩展查询到达后：`spawn_blocking(call_embedding_queries)` **批量**向量化（一次推理调用，替代逐条），
  再 `buffer_unordered(MAX_EXPANDED_QUERIES)` 并行 `hybrid_recall`；
- 取消语义：两路共用同一 `cancel`；join 后保留 `cancel.is_cancelled()` 检查点。

### 2.4 Embedding 去重（替换 char Jaccard）

- `core/search/query_plan.rs::dedup_expanded_queries(original_vec, vectors, threshold, max_keep)`：
  - 与原始查询向量 cosine ≥ `QUERY_DEDUP_SIMILARITY (0.92)` → 丢弃；
  - 与已保留扩展向量 cosine ≥ 0.92 → 丢弃；
  - 向量缺失时保守全保留（按 `MAX_EXPANDED_QUERIES` 截断）；
- 去重时机 = 向量化之后（向量反正要算，零额外推理）；按 kind 分域调参留作后续。

### 2.5 fail-open 全覆盖

| 失败点 | 降级（代码位置） |
|---|---|
| timeout / cancel | 空 `ExpansionResult` → 仅原始查询（`commands/llm.rs:1191-1202`） |
| LLM error / 重试耗尽 | `expand_queries` 返回空（`services/llm.rs:427-436`） |
| 无效 JSON / 解析失败 | 空列表（`parse_expansion_output` 尽力解析，不把噪声透传检索） |
| 扩展批量 embedding 失败 | `unwrap_or_default()` → 空，仅原始查询 |
| 单路检索失败 | 既有逻辑：向量失败跳该路，BM25 失败降纯向量（`hybrid_recall` 内） |

## 3. P1 落地清单（已实现）

### 3.1 `SearchHit.query_sources`（来源打标）

- `core/db/lance.rs:56-63`：`pub enum QuerySource { Original, Expanded(u8) }`；
- `SearchHit.query_sources: Vec<QuerySource>`（`#[serde(default)]`，旧数据兼容）；
- 打标：`commands/llm.rs:1382-1401`——扩展召回标 `Expanded(idx)`、原始标 `Original`、
  符号实体命中标 `Expanded(entity_base + eidx)`（`entity_base = kept_expanded.len()`）；
- 聚合合并：`core/agent/mod.rs::aggregate_hits` 去重时保留最高分命中的来源集。

### 3.2 跨查询一致性加成 `agreement_bonus`（`core/agent/mod.rs:549-581`）

- 统计文档所有 chunk 命中的**不同来源查询对**；
- **与查询多样性联动**：仅当来源查询对 cosine < `QUERY_DIVERSITY_THRESHOLD (0.85)`
  （视为"不同角度"）才计分；无向量可用的来源对保守计分；
- 文档代表分 = 最佳 chunk 分 + `agreement_bonus × AGREEMENT_BONUS_WEIGHT (0.05)`，clamp ≤ 1.0；
- 防"虚假共识"：三个相似查询命中同一文档不加分，三个异构查询命中才加。

### 3.3 `hybrid_recall` 拆分 + 池级精排 `rerank_pool`

- `core/indexer.rs:838` `hybrid_recall(dir, vec, query, top_k)`：查询理解 → Filter 前置 →
  多路召回 → RRF → 向量噪声过滤，**不含精排/聚簇**；`hybrid_search` 保持
  = `hybrid_recall` + 精排 + `finalize_hits`（kb_search 工具行为不变）；
- `core/indexer.rs:1291` `rerank_pool(pool, source_queries, min_score)`：
  1. 池级去重（`doc_name + chunk_index`，保留最高 RRF 分 + 合并来源）；
  2. 按**来源查询分组**分别精排（每个候选按命中它的来源查询各自 `rerank`），
     跨来源取 **sigmoid 分最大值**（证据叠加）；`total_pairs` 日志可观测精排调用量；
  3. 统一按 `min_score`（sigmoid 域）阈值过滤；精排不可用/失败回退 RRF 序；
- 收尾：`finalize_hits`（多样性聚簇 + 上下文窗口 + top_k 截断），与 kb_search 同语义。

## 4. P2 落地清单（已实现：符号实体变体）

方案中 P2 的 **Symbol Entity Discovery** 已提前落地（`commands/llm.rs:1282-1327`）：

- 触发：`plan.intent == Code && queries.len() < MAX_TOTAL_QUERIES`；
- 从原始 + 扩展查询提取符号 token（`extract_symbol_tokens`）→ 符号索引
  `Indexer::search_symbols(token, 3)`（确定性、零 LLM）→ 命中且非重复符号追加为
  `QuerySource::Expanded(entity_base + n)` 的 Entity 变体；
- 每 token 至多补一条；总查询数不超过 `MAX_TOTAL_QUERIES = 3`；
- 该路命中的候选同样进候选池参与池级精排。

## 5. 常量表（`core/agent/limits.rs`）

| 常量 | 值 | 含义 | 方案值 | 实现差异 |
|---|---|---|---|---|
| `MAX_EXPANDED_QUERIES` | 2 | 扩展查询数量上限 | 2 | — |
| `MAX_TOTAL_QUERIES` | 3 | 原始 + 扩展总查询数上限（防发散） | 3 | — |
| `QUERY_EXPANSION_TIMEOUT_SECS` | 5 | 扩展 LLM 调用独立总时限（秒） | 10 | **收窄到 5**（`limits.rs:36-40` 注释：慢端点 10s 几乎必然超时且白等，收窄少等 5s；正常端点 <5s 不受影响） |
| `QUERY_EXPANSION_RETRY_MAX` | 1 | 扩展调用重试次数（总尝试 = 重试 + 1） | 1 | **1 次**（🟠 L28 修复：5s 总时限下第 2 次重试需再等 4s 必然超时，旧值 2 使重试形同虚设；1 次覆盖瞬时抖动且不挤占时限） |
| `QUERY_DEDUP_SIMILARITY` | 0.92 | 扩展去重 cosine 阈值（≥ 视为重复） | 0.92 | — |
| `QUERY_DIVERSITY_THRESHOLD` | 0.85 | agreement 加成的查询对多样性阈值（cosine < 此值才计分） | 0.85 | — |
| `AGREEMENT_BONUS_WEIGHT` | 0.05 | 一致性加成系数（叠加到文档代表分） | 0.05 | — |

## 7. 量化收益目标与现状对照

方案 §6 的收益目标（对照实现状态）：

| 指标 | 测量方式 | 目标 | 现状 |
|---|---|---|---|
| 首答延迟 | `[agent_query] [1]` 扩展耗时 + `[2]` 检索耗时（trace 面板） | 扩展耗时从关键路径移除（与检索重叠） | ✅ 原始检索与扩展经 `tokio::join!` 并行，原始检索延迟被掩盖；⚠️ 但**流水线必须等 join 到点才进入下一阶段**，5s 超时仍位于首答关键路径（见 §8 L28） |
| LLM 调用次数 | `[llm] [输入语义扩展]` 日志 | 简单查询 0 次（规则门跳过），复杂查询 ≤1 次 | ✅ `should_expand` 规则门 + 一次性 `expand_queries`（含重试共 ≤3 次尝试，但总时限 5s 包裹） |
| 精排调用量 | `[indexer] [混合检索] 候选池精排: pool=.. pairs=..` 日志 | 跨查询重复 chunk 不再重复精排 | ✅ `rerank_pool` 池级去重后按来源查询分组计分；⚠️ 但 `rerank_pool` 无候选数上限（见 §8 M16） |
| 上下文冗余 | `[agent_query] [2]` 命中/去重统计 | 多查询去重后上下文更聚焦 | ✅ 池级去重 + `finalize_hits` 聚簇 |
| 扩展有效性 | `[agent_query] [2]` 各查询命中数 | 扩展独立命中占比可观测 | ✅ 日志按查询打印命中数；`query_sources` 可定位"被哪几个查询命中" |

## 8. 已知问题（如实记录）

引用《代码审查报告-RAG全链路P0批次.md》：

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| L28 | `limits.rs:40-43` | `QUERY_EXPANSION_TIMEOUT_SECS=5` + `RETRY_MAX=2` 不匹配：慢端点**首次调用即被 5s 掐断**，重试形同虚设；且该 5s 在 `tokio::join!` 下**位于首答关键路径**（方案 P0-5 声称"并行化后该时限已不在关键路径"，实际流水线仍要等它到点） | 慢模型端点上扩展功能实质失效（每次白等 5s），且拖慢首答 |
| M16 | `indexer.rs:1049-1054` vs `1291` | `rerank_pool`（多查询路径）**无精排候选上限**，每路 40-80 条 × 最多 5 查询全量精排（B2b 的 50 条上限只作用于 `hybrid_search`） | 多查询路径存在分钟级延迟风险，与单查询路径不一致 |
| M17 | `indexer.rs:1391-1396` | `rerank_pool` 将 RRF 域分数与 sigmoid 域分数**混排**（未标注候选追加后统一按 `score` 排序，跨域比较无意义） | 未标注候选排序失真（当前 agent 路径暴露面小） |
| M18 | `query_plan.rs:138-155` | `has_explicit_extension` 只校验扩展名**后**边界，不检查前导；`CODE_EXTENSIONS` 与 `is_code_query` 清单不一致（缺 c/cpp/h/rb/php） | `config.rs_backup`、`1.rs.old` 误判 Code；`main.c` 路由为 General（影响预检索触发面与 Filter 前置） |

**结论**：P0/P1/P2 主体按方案落地并全部 fail-open；慢端点体验（L28）与多查询路径精排成本（M16）
为当前已知短板，建议在下一迭代处理后再放开预检索扩展的默认收益评估。
