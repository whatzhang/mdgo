# mdgo 数据存储评审：结构 / 选型 / 业务匹配度 / 主流 Agent 对比 / 优化落地

> 最后更新：2026-08-23
> 版本：2026-08 · 评审范围：tauri/src-tauri（Rust 后端）+ 前端（index.html / main.html）全部数据存储
> 目标：验证「合适业务用合适存储」原则，找出性能与一致性可优化点，对比主流 Agent 存储方案，
> 并逐项标注优化项的落地状态（以当前代码为准）。
> 依据：全量源码调查（`docs/data_storage_analysis.md` 前序调查）+ 本次专项核实。

---

## 0. 结论摘要

mdgo 的存储选型**整体合理**（SQLite 承载结构化持久、LanceDB+BM25 分层检索、内存一切有界），
与主流 Agent（Claude Code / Cline / Pi / Reasonix）的存储实践同构。评审期发现的 7 个可优化点
中 **O1/O2/O3/O5/O6 已落地**（记忆向量召回、记忆过期、记忆 FTS5、配置统一加载、索引增量批处理），
O7（挂起表显式上限）未做、O4（会话写入批量化）保持待量测。RAG 本地栈在评审后又显著增强
（token 预算分块、embedding 持久缓存、标签检索、rerank 缓存、代码符号检索路）。

## 1. 现状与业务匹配度逐项评审

| 业务 | 现状存储 | 匹配度 | 评审意见 |
|---|---|---|---|
| 对话/会话/消息 | SQLite `{dir}/.mdgo/mdgo.db`（WAL+IMMEDIATE；`chat_messages` / `chat_sessions` 表） | ✅ 合适 | 与 Claude Code/Cline 同构（会话用 SQLite）。分支/压缩检查点作为表字段演进（`parent_id`/`branch_point`/`compaction_state`）合理。**可优化（O4 未落地）**：流式消息逐条 INSERT，长会话高频写 |
| 文档检索 | LanceDB `vectors` + tantivy `bm25`（schema v5）+ 符号路 + RRF 融合 + rerank | ✅ 合适 | 分层检索符合检索范式，且已含 token 预算分块、embedding 持久缓存、标签检索、rerank 缓存（见 §3 增强项） |
| 历史对话检索 | LanceDB `chat_vectors`（独立表） | ✅ 合适 | 与文档向量分表隔离，重建互不影响；增量追加，无 BM25 |
| 长期记忆 | SQLite `{系统数据目录}/com.mdgo/memory.db` `memory_items`（系统级全局共享） | ✅ 已增强 | revision 审计链对齐 Reasonix；**O1 向量召回 / O2 过期 / O3 FTS5 均已落地**（见 §3）；另有两级隔离（`scope='project'` 按 `dir_path` 归属知识库 ∪ `scope='global'` 跨库） |
| 技能 | SQLite（mdgo.db 技能表 + 指标 `skill_exec_metrics`）+ `resources/skills/*/SKILL.md` + 内存注册表 | ✅ 合适 | 指标落库（带 request_id）与文件化规约分离正确 |
| 提示词模板 | SQLite **知识库级 PromptStore**（`{dir}/.mdgo/mdgo.db` 的 `prompts` 表） | ✅ 合适 | 早期「全局 `prompts.db`」已移除，提示词改为按知识库隔离存储，与知识库级统一库共用（`services/prompt.rs`） |
| 配置 | JSON `setting.json` + 内存 `LlmConfig`/`ConfigStore` + YAML `approval.yaml`/`agent_tools.yaml` + plugin-store `app_settings.json` | 🟡 已收敛 | O5 已落地：Tauri 模式统一经 `kb_save_setting`/`kb_load_setting` 读写（写 setting.json + 同步内存），消除前端 FSA 与后端双通道写竞争；本地直开模式保留 JSON 直写 |
| 外部工具/审批策略 | YAML（全局，缺失降级不阻断） | ✅ 合适 | 策略/扩展类配置用 YAML（可读可 diff），与运行配置分离正确 |

| 可观测 | 日志文件 + SQLite 指标 + 内存 TraceBus | ✅ 合适 | tracing 双输出 + 指标落库，够用（未达 OTel 级，非缺陷） |
| 模型资产 | 文件系统（按平台 ONNX） | ✅ 合适 | 模型下载缓存，标准做法 |

## 2. 主流 Agent 存储方案对比

| 维度 | mdgo | Claude Code | Cline | Pi（编码 Agent） | Reasonix |
|---|---|---|---|---|---|
| 会话存储 | SQLite（每知识库 `mdgo.db`，分支/压缩检查点作列） | SQLite（`~/.claude/projects/`，消息/会话） | SQLite（WAL，会话+任务） | **JSONL 追加式**会话文件 + `/tree` 分支 + compaction entry（`retainedTail` 自包含检查点） | SQLite + 会话存档可检索 |
| 记忆 | SQLite 结构化记忆（revision 审计链 + **FTS5 倒排 + 向量召回 + 过期治理**，两级作用域） | 无显式记忆层（靠 CLAUDE.md + 会话历史） | 无独立记忆（会话历史为主） | 无独立记忆（会话/分支摘要替代） | **结构化记忆**（memory/remember/forget + revision + 自动写入授权 + 可选向量） |
| 文档 RAG | LanceDB 向量 + tantivy BM25 + 代码符号路 + RRF + rerank（**全本地**，token 预算分块 + embedding 持久缓存 + 标签检索） | 无内置（外部 MCP/知识库） | 可选向量库（自定义 RAG） | 无内置（`@file` 引用 + 上下文文件） | 无内置（agent 工具面 + 记忆检索） |
| 配置 | JSON+内存统一后端读写（O5 落地）+ YAML 策略 | `settings.json` + CLAUDE.md | `settings/` 多文件 | `settings.json` + `auth.json` + context 文件分层 | `reasonix.toml` + REASONIX.md/AGENTS.md 分层 |
| 上下文压缩 | 摘要+滑窗（SQLite `compaction_state` 检查点 + `session_skills` 恢复） | 自动压缩（会话内） | 自动压缩 | **compaction**（token 精确、keepRecent、split turn、retainedTail） | 按需加载 + token 经济 |
| 工具/扩展配置 | YAML 外部工具（HTTP 适配器）+ MCP + 硬编码内置 | MCP（JSON 配置） | MCP | 扩展（TS 代码）+ skills（渐进披露） | MCP + Skills + 插件 |
| 可观测 | 日志 + SQLite 指标 + 内存 TraceBus | 日志 | 日志 | `pi-debug.log` + 完整事件流 | trace + 步骤记录 |

**对比结论**：
1. **会话**：mdgo 的 SQLite 方案与 Claude Code/Cline 一致（随机读、分支、统计友好），
   优于 Pi 的纯 JSONL（流式写轻但随机读/统计弱）。Pi 的 `retainedTail` 自包含检查点
   值得借鉴（mdgo 检查点已是同构思路）。
2. **记忆**：mdgo 已对齐 Reasonix 的 revision 审计链，且在**检索增强**上补齐
   （FTS5 倒排 + 向量召回 + 过期过滤），检索能力已不低于 Reasonix 的「可选向量」。
3. **RAG**：mdgo 的全本地检索栈（向量 + BM25 + 符号路 + rerank，配 token 预算分块、
   embedding 持久缓存、标签检索、rerank 缓存）在主流 Agent 中仍属少见完整实现，
   是优势项。
4. **配置**：O5 落地后 mdgo 配置入口碎片化已显著缓解（配置写回统一经后端命令）。

## 3. 优化项清单（按优先级）与落地状态

### P1 — 性能/正确性相关

| # | 优化点 | 现状（评审期） | 落地状态（2026-08-23 核实） |
|---|---|---|---|
| O1 | **记忆检索接向量** | `memory_items` 关键词打分 | ✅ **已落地**：`search_hybrid`（关键词 ∪ 向量，按 id RRF 融合，kw 0.4 / vec 0.6，k=60）；`MemoryVectorIndex` 内存向量索引（记忆规模小，惰性增量 `sync` + 删除清理 `prune`，embedding 依赖倒置可测）；已接入 `search_memory` 工具与生成前注入（`commands/llm.rs`）；向量路失败自动降级纯关键词 |
| O2 | **启用记忆过期/衰减** | `expires_at` 字段已定义未使用 | ✅ **已落地**：`list`/`search`/`list_visible` 均过滤 `expires_at`（有值且 ≤ now 不召回不注入）；`remember` 工具支持 `expires_in_days`（`loop_tools.rs`）；`MemoryItem::is_expired` 提供判定 |
| O3 | **记忆关键词倒排** | 无 FTS5 | ✅ **已落地**：`memory_fts` FTS5 虚拟表（`tokenize='unicode61'`，id UNINDEXED），检索走 `MATCH ... ORDER BY bm25(memory_fts)`；写后全量重建（记忆规模小可接受）；建表失败降级关键词打分；顺带清理旧版残留触发器 |
| O4 | **会话写入批量化** | 流式消息逐条 `save_message` INSERT | ⏳ **未落地（保持待量测）**：`save_message` 仍为单条写入（单写事务：幂等筛查 + 插入 + 会话统计原子完成）；评审建议先量测真实写频率，再决定消息+轨迹合并批写与压缩检查点降频 |

### P2 — 一致性/工程化

| # | 优化点 | 现状（评审期） | 落地状态（2026-08-23 核实） |
|---|---|---|---|
| O5 | **配置统一加载层** | setting.json（前端 FSA）+ app_settings.json（plugin-store）+ approval.yaml/agent_tools.yaml（后端 YAML）+ LlmConfig（内存） | ✅ **已落地**：Tauri 模式统一经后端 `kb_save_setting`/`kb_load_setting`（写 setting.json + 同步内存 LlmConfig，消除前端 FSA 与后端双写竞争）；本地直开模式保持 JSON 直写；后端失败回退本地写入不阻断 |
| O6 | **索引增量批处理** | BM25/Lance 增量写入（watcher 驱动） | ✅ **已落地**：文件变更经 notify → debounce actor 合并（`core/watcher.rs` 防抖窗口 2000ms）→ 批量触发索引更新；技能事件独立 debounce 循环 |
| O7 | **挂起表显式上限** | approval_pending / plan_pending 无条数上限（60s 超时兜底） | ❌ **未做**：仍为 `HashMap`（60s 超时 fail-closed + RAII `RemovePendingOnDrop` 清理防残留）；极端并发可短暂堆积，建议与 ToolCallBus 一致设容量上限 + 满则清理最旧 |

### RAG 本地栈增强（评审后新增，代码已核实）

- **token 预算分块**：`core::db::token_budget::ChunkBudget` 按 embedding 模型窗口推导
  `chunk_size`/`chunk_overlap`（**语义为 token 数**，512 窗口 overlap 默认 56），
  `TokenBudgetValidator` 硬上限裁决 + 超限二次切分/显式降级截断；
- **embedding 持久缓存（P0-5）**：`{dir}/.mdgo/embedding_cache.sqlite` 单表
  （键 = `model|dimension|content_hash`，FNV-1a 128 哈希；上限 100k 条 ≈150MB，
  按最旧裁剪）——增量索引只对内容变化的 chunk 重新推理；
- **查询 embedding 内存缓存**：`query_embedding_cache`（容量 512，FIFO），同一查询
  文本重复命中免重复推理；
- **标签检索**：frontmatter `tags` 入列（LanceDB `vectors.tags` 列 + bm25 `tags`
  字段带 boost 2.0），查询侧 `query_plan` 提取 `#标签` 过滤；
- **rerank 缓存**：`RerankScoreCache`（容量 2048，FIFO），精排结果复用；
- **代码符号检索路**：intent=Code 时按符号名精确/前缀召回（LanceDB
  `symbol_name`/`symbol_kind` 列），与向量/BM25 并行后 RRF 融合，符号命中可
  `symbol_name` 佐证放行；
- **bm25 schema v5**：`SCHEMA_VERSION="5"`，tantivy schema 变更自动重建
  （版本标记 + Jieba 中文分词 + msm 查询）。

### 暂不建议动（保持现状）

- 文档检索 LanceDB+BM25+rerank 本地栈：已是优势，勿改。
- 会话 SQLite（非 JSONL）：与主流一致且分支/检索友好。
- 内存有界结构：容量治理已齐备。
- 日志/指标：够用。

## 4. 落地建议

- **✅ 已完成（2026-08 批次，含未提交 RAG P0 批次改动）**：
  - **O1 记忆向量检索**：`search_hybrid` + `MemoryVectorIndex`（内存索引、惰性增量 +
    prune、RRF 融合、向量路失败降级关键词），接入 `search_memory` 工具与生成前注入。
  - **O2 记忆过期**：`expires_at` 启用（list/search/list_visible 过滤），
    `remember` 工具支持 `expires_in_days`。
  - **O3 记忆 FTS5**：`memory_fts` 虚拟表 + bm25 排序检索（写后全量重建，
    FTS 不可用降级关键词打分）；顺带修复历史残留触发器导致的 SQLITE_ERROR。
  - **O5 配置统一加载层**：Tauri 模式统一经后端 `kb_save_setting`/`kb_load_setting`
    （写 setting.json + 同步内存 LlmConfig，消除前端 FSA 与后端双写竞争）；
    本地直开模式保持现状；后端失败回退本地写入不阻断。
  - **O6 索引增量批处理**：watcher 2s 防抖批量触发索引更新。
- **O4（会话写入批量化）**：评审已注明「先量测真实写频率再决定」；改动涉及前端
  保存链路与后端事务，需量测数据支撑后谨慎实施。
- **O7（挂起表显式上限）**：未做但风险可控（60s 超时 fail-closed + RAII 清理），
  建议后续与 ToolCallBus 对齐加容量上限。

> 备注：本评审为源码静态核实；O4 的「写放大」严重度建议在真实长会话场景用日志/指标
> 验证后确认优先级。
