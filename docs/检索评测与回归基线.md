# 检索评测与回归基线

最后更新：2026-08-23

> 检索质量度量闭环（P0-3）：**每次修改 chunk / BM25 / RRF / reranker / query planner / metadata 后，
> 都应跑一遍本基准**，用 Recall / MRR / NDCG / Latency 判断改动是变好还是变差，并把结果记入版本基线表。
> 实现位于 `tauri/src-tauri/src/bin/benchmark.rs`；评测数据与首轮基线见 `retrieval_eval/`。

---

## 1. 用法

在 `tauri/src-tauri` 目录下执行：

```text
cargo run --bin benchmark --features bench -- --kb <知识库目录> --queries <queries.jsonl> --expected <expected.jsonl> [--topk 20] [--reindex] [--yes-wipe]
```

> 🟠 L31/M25：`benchmark` bin 通过 `bench` feature 启用（`required-features`，默认构建不暴露
> `core` 层 API 面）；`--reindex` 检测到目标目录已有 `.mdgo` 索引数据时**必须加 `--yes-wipe`**
> 显式确认（且先退出正在运行的应用），防止误清空索引与 embedding 缓存。

参数说明：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--kb <dir>` | 是 | 被测知识库根目录（语料根） |
| `--queries <file>` | 是 | 查询集（JSONL） |
| `--expected <file>` | 是 | 期望标注集（JSONL） |
| `--topk <n>` | 否 | 召回上限，默认 20（Recall@20 / NDCG@10 的截断基数；非法值报错） |
| `--reindex` | 否 | 先全量重建索引再评测（修改分块/BM25/schema 后必须加） |
| `--yes-wipe` | 否 | `--reindex` 时显式确认清空已有 `.mdgo` 索引/缓存 |
| `--help` | 否 | 打印用法 |

示例（仓库自带基准集）：

```text
cd tauri/src-tauri
cargo run --bin benchmark --features bench -- --kb G:\gitProject\mdgo --queries ..\..\retrieval_eval\queries.jsonl --expected ..\..\retrieval_eval\expected.jsonl --topk 20 --reindex --yes-wipe
```

运行前需保证本地 embedding 模型就绪（`benchmark.rs` 启动时会调用
`core/db/utils::ensure_model_ready` 初始化模型，分块预算/查询向量依赖真实模型窗口）。

> ⚠️ **`--reindex` 有数据风险**：它会先清空目标目录的 `.mdgo` 索引（LanceDB + BM25）与
> embedding 缓存，再按默认配置全量重建；若与运行中的 App 并发写同一 `.mdgo` 可能损坏索引
> （详见《代码审查报告-RAG全链路P0批次.md》M25）。**执行前请先退出 App**，并确认目标目录确实是要重建的库。

## 2. 数据格式

### 2.1 queries.jsonl（查询集）

每行一条查询，字段：`id` / `query` / `intent` / `difficulty` / `language`：

```json
{"id": "q001", "query": "为什么 embedding 后英文 chunk 数量特别多", "intent": "semantic", "difficulty": "medium", "language": "zh"}
{"id": "q011", "query": "how does rrf fusion work", "intent": "semantic", "difficulty": "hard", "language": "en"}
{"id": "q015", "query": "index_all 函数在哪个文件", "intent": "code", "difficulty": "easy", "language": "zh"}
```

`intent` 取值：`semantic` / `code` / `exact` / `navigation` / `cross` / `entity` / `tag`。

### 2.2 expected.jsonl（期望标注）

每行一条标注，字段：`query_id` / `relevant_documents` / `relevant_chunks`：

```json
{"query_id": "q001", "relevant_documents": ["docs/分块 Token 预算设计.md", "docs/代码审查报告-RAG全链路P0批次.md"], "relevant_chunks": []}
```

- `relevant_documents` = "**应该被召回的文档**"（Recall 目标），**必须与索引输出的
  `doc_name` 精确一致**（相对路径，`scan_directory` 的 `strip_prefix(base)` + 反斜杠转正斜杠）；
- `relevant_chunks`：chunk 级标注（`benchmark.rs` 已定义字段，**第一版指标按 doc 级计算**，
  只判断方向够用；chunk 级评测留待 V2）；
- 标注宁精勿滥——误标会直接污染指标（`benchmark` 对缺失标注的查询会跳过并在结尾提示）。

### 2.3 当前基准集（v1，42 条）

- 文件：`retrieval_eval/queries.jsonl`（42 条）+ `retrieval_eval/expected.jsonl`
- 覆盖 9 类：中文语义(10) / 英文(4) / 代码符号(10) / 精确查找(4) / 文件导航(4) /
  跨文档(4) / 实体符号(3) / 标签主题(3)
- 难度分布：easy 14 / medium 22 / hard 6
- 语料基准：本仓库自身（KB 根 = 仓库根目录）

## 3. 指标说明

### 3.1 doc 级判定（去重）

`hybrid_search` 返回的 hits 按 `doc_name` 去重（保持首次出现顺序）后再计算指标，
避免同一文档的多个 chunk 命中虚高 Recall / 干扰 MRR。

### 3.2 指标定义

| 指标 | 定义 | 关注点 |
|---|---|---|
| Recall@K | 前 K 个去重文档中相关文档数 / 相关文档总数（K = 5 / 10 / topk） | 召回稳不稳，第一道关 |
| MRR | 首个相关文档排名的倒数（无命中记 0） | "对不对" |
| NDCG@K | 排序质量（DCG / IDCG，K = 5 / 10） | 相关文档是否排前面 |
| Latency | 每查询全链路总耗时（查询向量化 + 向量 + BM25 + RRF + reranker + 聚簇），输出 avg 与 p95 | 延迟 |

### 3.3 分阶段耗时（RetrievalTimings）

`benchmark.rs` 每查询明细行之后会打印最近一次检索的分阶段耗时
（来源：`core/types.rs::RetrievalTimings`，通过 `Indexer::last_retrieval_timings` 读取）：

```text
[benchmark]   → planner=1ms dense=18ms bm25=22ms symbol=0ms rrf=1ms rerank=54ms finalize=2ms
```

| 字段 | 含义 |
|---|---|
| planner | 查询理解（intent 路由 + 符号提取 + Filter 构造） |
| dense | 向量路召回 |
| bm25 | BM25 路召回 |
| symbol | 符号路召回（Code 意图） |
| rrf | RRF 融合 |
| rerank | cross-encoder 精排（未启用为 0） |
| finalize | 聚簇 + 上下文扩展 |
| total | 全链路 |

定位延迟瓶颈时优先看这一行（如"rerank 不截断占 90%+ 延迟"就是从它读出的）。

## 4. 首轮基线数据

来源：`retrieval_eval/README.md`（"版本基线记录"表）。

| 版本/改动 | Recall@10 | MRR | NDCG@5 | Latency avg | 备注 |
|---|---|---|---|---|---|
| 基线 v1（首跑） | 0.683 | 0.539 | 0.509 | 5644ms | 项目根 3567 文件 / 26 万 chunk；rerank 不截断占 90%+ 延迟 |
| rerank 截断 30 | 0.548 | 0.517 | 0.469 | 1169ms | 延迟大降但漏 RRF 30 名外相关文档 |
| **基线 v2（截断 50 + 基准集修正）** | **0.605** | **0.519** | **0.479** | **1290ms** | 延迟/精度折中；avg -77% vs 首跑 |

**当前回归基线 = 基线 v2**（截断 50 + 基准集修正后）。

## 5. 回归流程

1. **改前**：记录当前基线（版本/改动、Recall@10、MRR、NDCG@5、Latency avg）。
2. **改后**：修改 chunk / BM25 / RRF / reranker / query planner / metadata 之后，
   按 §1 跑一遍；分块/BM25/schema 相关改动必须带 `--reindex`。
3. **对比**：对比 Recall@10 / MRR / NDCG@5 是否劣化、Latency avg 是否可接受；
   结合分阶段耗时定位新增延迟来自哪一段。
4. **记录**：把结果追加进"版本基线表"（见 `retrieval_eval/README.md` 的表格格式），
   一行一版：

```text
| 日期 | 版本/改动 | Recall@10 | MRR | NDCG@5 | Latency avg | 备注 |
|---|---|---|---|---|---|---|
| 2026-08-23 | 示例改动 X | 0.610 | 0.520 | 0.481 | 1350ms | ... |
```

> 判定原则：指标下降需要可解释的原因（如延迟换精度）；无解释的 Recall/MRR 下降视为回归。

## 6. 已知局限

- **语料为项目自身**：含 css_js/cdn 大 `min.js` 与 5 万行 HTML 噪声，指标天然偏低；
  真实笔记知识库的预期指标更高，横向对比请用同语料。
- **中文查询 vs 英文代码标识符**（q042 类）：符号路只对 CamelCase/snake_case 查询词生效。
- **tag 类查询**：当前仓库语料无 frontmatter，tag 类查询命中依赖正文/标题主题词，
  `tags` 字段的收益需用**带 frontmatter 的语料**单独验证。
- **缺失标注的查询不计入指标**：`benchmark` 末尾会提示跳过数量，请保持基准集完整。
