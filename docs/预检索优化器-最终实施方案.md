# 预检索优化器（Pre-Retrieval Optimizer）最终实施方案

> **归档状态**：本方案已按《预检索优化器-实施归档.md》完成 P0/P1/P2 落地（`cargo check` + 单测通过）。
> 本文档保留为方案设计基线；实施细节、文件映射与行为变化以实施归档为准。

> 定位：把现有「输入语义扩展（固定 3 条 Query 改写）」收敛为**一次性、低延迟、结构化、可失败降级的预检索优化器**。
>
> 一句话工程目标（替代"超过主流 Agent"）：
> **让 Agent 第一次检索就拿到更高覆盖率、更低冗余、更高证据一致性的上下文，同时不增加一个新的 Agent Loop。**
>
> 本方案基于《自适应查询规划方案评估.md》的裁决，吸收收敛意见，落实到具体代码位置与落地顺序。
> 前置阅读：评估文档 §2（三个根本性判断：检索路径零 LLM 开销 / 不做第二 Agent 循环 / 预检索只服务首答延迟与首屏上下文质量）。

---

## 1. 最终架构：四层边界

```
┌─────────────────────────────────────────────┐
│                Agent Layer                  │
│  推理 / 工具调用 / 多轮                      │
│  kb_search / code_lookup / 自主补检索        │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│          Pre-Retrieval Intelligence         │
│  规则门 should_expand                        │
│       ↓                                     │
│  一次性 LLM Expansion（0~2 条）              │
│       ↓                                     │
│  Embedding 去重 + 格式校验                   │
│       ↓  （全部 fail-open）                 │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│             Retrieval Engine                │
│  向量 + BM25 + 符号 多路召回                 │
│       ↓                                     │
│  RRF 融合                                   │
│       ↓                                     │
│  Candidate Pool（跨查询合并）                │
│       ↓                                     │
│  Pool Rerank（按来源查询计分 + max）         │
│       ↓                                     │
│  Diversity / Context                        │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              Knowledge Index                │
│  向量 / BM25 / 符号 / 元数据                │
└─────────────────────────────────────────────┘
```

**边界纪律**（违反即退回重做）：
- 预检索层每请求至多 **1 次** LLM 调用；"不够就再搜"归 Agent 层；
- 检索路径（`hybrid_search` 内部、kb_search 工具）**零 LLM 开销**（`query_plan.rs` 既有原则）；
- 任何 LLM 输出/扩展失败都 fail-open 到"原始查询单跑"。

---

## 2. 模块收敛：Query Expansion = 一个很小的模块

```
Query Expansion
│
├── should_expand(query, plan)      ← 规则（零 LLM）
├── LLM 生成 0~2 条                  ← 唯一 LLM（一次调用）
├── 格式校验                        ← deterministic（复用 JSON Schema 校验）
├── embedding 去重                  ← deterministic（cosine ≥ 0.92）
└── fail-open                       ← deterministic（timeout/cancel/解析失败→原始查询）
```

**不做**：Planning / Decomposition / Feedback / Replanning / Entity Discovery / Knowledge Graph（这些职责分属 Agent 层或 Phase 2/3 独立立项）。

## 3. P0：Phase 1 详细设计（先落地）

### P0-1 原始检索与扩展并行

**现状**（`commands/llm.rs`）：Stage 1 `expand_queries` 串行 await（:1241），Stage 2 才开始检索（:1277）——LLM 延迟阻塞首答。

**改造**：

```rust
// Stage 1+2 重构（commands/llm.rs）
let original_fut = async {
    // 原始查询立即 embedding（单独 spawn_blocking）→ hybrid_search
    search_single(&state, &dir_path, &query, effective_top_k).await
};
let expansion_fut = async {
    // LLM 扩展带独立总时限（见 P0-5）
    tokio::time::timeout(
        Duration::from_secs(QUERY_EXPANSION_TIMEOUT_SECS),
        llm.expand_queries(&query, &messages, cancel.clone()),
    )
    .await
    .unwrap_or_default()          // 超时 → 空 Vec → fail-open
};
let (original_hits, expanded) = tokio::join!(original_fut, expansion_fut);

// 扩展到达后：批量 embedding（P0-3）→ 并行检索（buffer_unordered(2)）→ merge all_hits
```

- 取消语义：两路共用同一 `cancel`（扩展内部 `retry_loop` 已响应取消；检索路沿用现有 `take_until(cancel_fut)` 模式）；join 后保留现有 `cancel.is_cancelled()` 检查点（:1255）。
- 扩展为空/失败 → 只提交原始命中，**原聚合路径不变**。

### P0-2 自适应扩展：规则决定"要不要"，LLM 决定"几条"

**规则门 `should_expand`**（放 `core/search/query_plan.rs`，与 `should_plan` 同风格，零 LLM）：

```rust
pub fn should_expand(query: &str, plan: &QueryPlan) -> bool {
    let q = query.trim();
    if q.is_empty() { return false; }
    if q.chars().count() < 8 { return false; }            // 超短查询
    if plan.intent == RetrievalIntent::Code
        && plan.symbols.iter().any(|s| s.len() >= 2) { return false; } // 纯符号/精确代码检索
    if is_file_path_like(q) { return false; }             // main.rs / Cargo.toml / a/b.ts
    true
}
```

- `is_file_path_like`：单 token 且含扩展名（`^[\w.-]+\.[a-z0-9]+$`）或含路径分隔符。
- 判定"不要扩展"的查询（`Redis`、`main.rs`、`UserService`）直接走原始检索，省一次 LLM。

**LLM 侧**：prompt 由"输出 3 行"改为"输出 0~2 条，不足 2 条时不要凑数"；上限常量：

```rust
// core/agent/limits.rs
pub const MAX_EXPANDED_QUERIES: usize = 2;   // 扩展上限（商用默认 2）
pub const MAX_TOTAL_QUERIES: usize = 3;      // 原始 + 扩展
```

**原因**（用户判断成立）：每个查询后面是 嵌入+BM25+向量+符号+RRF+精排+聚簇 全管线，3 条扩展 = 4 次昂贵检索；2+1 是延迟/收益的商用平衡点。

### P0-3 Batch Embedding（含修正）

- 新增 `core/db/utils.rs`：

```rust
pub fn call_embedding_queries(texts: &[&str]) -> Result<Vec<Vec<f32>>, String> {
    let prefixed: Vec<String> = texts.iter()
        .map(|t| format!("{}{}", BGE_QUERY_INSTRUCTION, t))
        .collect();
    let refs: Vec<&str> = prefixed.iter().map(|s| s.as_str()).collect();
    call_embedding(&refs, None)          // 内部 BATCH_SIZE=128 批量推理
}
```

- **修正（重要）**：不要 `[original, q1, q2]` 一批——那会让原始查询 embedding 等 LLM 返回，破坏 P0-1。正确组合：
  - 原始查询：**立即**单独 embedding + 检索（不等 LLM）；
  - 扩展查询（0~2 条）：LLM 返回后**合一批** `call_embedding_queries`，一次 `spawn_blocking`（替代现在的 2~3 次独立 `spawn_blocking`，`commands/llm.rs:1286-1292`）。

### P0-4 Embedding 去重（替换 char Jaccard）

- 去重时机挪到**向量化之后**（候选反正都要 embedding，零额外推理）。
- 初始阈值 `QUERY_DEDUP_SIMILARITY = 0.92`，接口预留参数：

```rust
// core/search/query_plan.rs 或 utils
pub fn is_duplicate_query(a: &[f32], b: &[f32], threshold: f32) -> bool {
    cosine(a, b) >= threshold
}
```

- 未来按 kind 分域调参（Keyword 0.90 / Semantic 0.94 / Entity 0.96），Phase 1 不实现，只留参数入口。
- 保留现有"与原始查询相似度过高丢弃"语义（用 embedding 距离替代 `char_jaccard < 0.6`）。
- 同时：**新增实体的查询不算重复**（`Redisson RLock` vs `Redis 分布式锁` 语义近但实体增益大）——entity 增益判定 Phase 2 用符号索引实现，Phase 1 至少不要误杀。

### P0-5 独立总时限（比 30~60s 更激进，用户修正采纳）

```rust
// core/agent/limits.rs
pub const QUERY_EXPANSION_TIMEOUT_SECS: u64 = 10;   // 10~15s 按本地模型 benchmark 调
```

**实现要点**：
- 用 `tokio::time::timeout` 包裹**整个扩展调用**（含重试），而非只改 HTTP 客户端超时——因为 `retry_loop`（2s 起退避 ×3 次）叠加后最坏可达 4 次 × 各自超时，远超 10s；
- 同时把扩展调用重试降为 **1 次**（`EXPANSION_RETRY_MAX = 1`），预检索预算从紧；
- 超时/取消/LLM 错误/无效 JSON → 空 Vec → fail-open。**并行化后该时限已不在首答关键路径上**，这正是 P0-1 的价值。

### P0-6 fail-open 全覆盖（现状保留 + 补位）

| 失败点 | 降级 |
|---|---|
| timeout / cancel | 空 Vec → 原始查询 |
| LLM error / 重试耗尽 | 空 Vec → 原始查询 |
| 无效 JSON / 解析失败 | 空 Vec → 原始查询 |
| embedding 失败（批量） | 该批跳过；原始查询命中已就绪 |
| 单路检索失败 | 现有逻辑：向量失败跳该路，BM25 失败降纯向量（`indexer.rs:847-863`） |

**铁律：扩展模块任何失败不得导致整个 RAG 失败。**

## 4. P1：Phase 2 详细设计（只做两项）

### P1-A `SearchHit.query_sources` + Cross-Query Agreement

**数据结构**（`core/db/lance.rs:53` SearchHit 增加字段，`#[serde(default)]` 保证序列化兼容）：

```rust
#[derive(Debug, Clone, Copy, Serialize, Deserialize, PartialEq)]
pub enum QuerySource { Original, Expanded(u8) }   // u8 = 扩展序号

pub struct SearchHit {
    // ...现有字段
    #[serde(default)]
    pub query_sources: Vec<QuerySource>,
}
```

**写入路径**：`commands/llm.rs` Stage 2 每路检索后打标；`aggregate_hits` 去重时（`agent/mod.rs:1002-1017`）合并来源（保留最高分命中的来源集）。

**Agreement 不粗暴加分（用户修正采纳）**——与查询多样性联动：

```rust
// 伪代码：一致性命中加成 = f(来源数, 来源查询间多样性)
agreement_bonus(doc) = sum over source pairs { cosine(q_i, q_j) < 0.85 ? +w : 0 }
```

- 三个相似查询命中 A（`Redis 分布式锁` / `Redis 分布式锁实现` / `Redis 分布式锁代码`）→ 多样性低 → 不加分，避免**虚假共识**；
- 三个异构查询命中 A（`Redis 分布式锁` / `Redisson RLock` / `Redis Lua 原子锁`）→ 多样性高 → 加分，证据可靠。
- **零额外成本**：查询向量 P0 已算，pairwise cosine 直接用。

**调试价值**：`rag:done` 引用来源可展示"被几个查询命中"，配合现有 `[agent_query] [2]` 日志定位召回问题。

### P1-B Candidate Pool 统一 Rerank（含修正）

**现状**：`hybrid_search` 内部每查询一次精排（`indexer.rs:945-986`），3 个查询 = 3 次 cross-encoder 推理。

**修正后设计**（cross-encoder 必须带查询，见 `rerank.rs:36-47`）：

1. **拆分 `hybrid_search`**：新增 `hybrid_recall(dir, vec, query, top_k) -> Vec<SearchHit>`（召回 + RRF + 向量噪声过滤，**不含精排**，即现有 `:905-942` 段的产物）；`hybrid_search` 改为 `hybrid_recall` + 精排 + 聚簇（保持 kb_search 工具行为不变）。
2. **池级合并**（`commands/llm.rs`）：多查询的 `hybrid_recall` 结果按 `doc_name + chunk_index` 去重合并 → Candidate Pool。
3. **池级精排**：对每个候选，**按命中它的来源查询**分别 `rerank(query_i, [candidate], min_score)` 取 max（跨查询重复 chunk 只推理一次；同候选多来源才增加对比次数，量级 ≤ 原方案）。`LocalBgeReranker` 复用（`rerank.rs:263`）。
4. 精排失败 → 回退池级 RRF 排序（保持现有降级语义 `indexer.rs:970-977`）。

**收益**：跨查询重复 chunk 的精排调用数从 `Σ每查询候选数` 降到 `去重后候选数`；`rerank_min_score` 在统一 sigmoid 域裁决一次；为 P1-A agreement 特征提供统一分数域。

> 说明：用户方案"ONE Rerank"在 cross-encoder 语义下不成立（精排必须知道 query），本设计是其**可行等价物**——成本节省来自池级去重而非单次调用。

## 8. 风险与护栏（增量）

| 风险 | 护栏 |
|---|---|
| 并行后 embedding/rerank CPU 并发叠加 | 原始 embedding 单独 + 扩展批量一次；池级精排仍走 `spawn_blocking`，`GLOBAL_SESSION` Mutex 天然串行（`embedding.rs:76`、`rerank.rs:56`） |
| 规则门误跳过应扩展的查询 | `should_expand` 保守（只跳过确定性场景：超短/文件路径/纯符号）；误判仅损失扩展收益，不影响正确性 |
| 10s 时限内本地慢模型来不及 | fail-open 到原始查询，且原始检索已并行进行；时限按 benchmark 调 10~15s |
| `query_sources` 破坏前端序列化 | `#[serde(default)]` + 前端仅展示 doc_name/score（现字段不动） |
| 池级精排分数域混乱 | 严格遵循 `aggregate_hits` 三分域契约（sigmoid/RRF/符号），池级精排统一写 `score_rerank` |
| 功能膨胀回"小 Agent" | 硬性检查：预检索层 LLM 调用次数 ≤1/请求；无循环、无状态、无持久化 |

## 10. 结论

本方案与现有 mdgo 架构完全对齐：**预检索层一次性、确定性、可降级；Agent 层保持唯一的自适应循环**。落地顺序固定为 P0（并行 + 0~2 自适应 + 批量 embedding + 去重 + 10s 时限）→ P1（来源追踪 + 池级精排 + 一致性加分）→ P2（符号实体发现 / 结构检索 / 别名图）。

护城河不是"再堆一个 LLM Planner"，而是把已有的 `RuleQueryPlanner + Vector + BM25 + Symbol + RRF + Reranker + Diversity + Context Window + Agent Tool Loop` 通过**一次性 Query Expansion + Candidate Pool Fusion** 正确组合。
