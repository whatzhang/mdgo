# 知识画布（Knowledge Canvas）

## 核心原则

> **Canvas 是一种 JSON 文件格式，不是 AI 工具。**

- **模型负责**：理解知识、设计节点与关系、**分析知识结构并声明布局意图**（layout）。
- **工具负责**：`read`（读取 .canvas 或知识库文件）、`write`（写入 .canvas）、`kb_search`（检索真实资料）。
- **系统负责**：Canvas Schema 校验、ID 唯一化、edge 引用校验、file 路径安全校验、**布局坐标计算**、原子写入。

**禁止调用任何 Canvas 专用 Function（不存在）；生成/整理画布全部通过 `write` 写入 .canvas 完成。**

**布局分工（关键）**：模型声明「布局意图」（用哪种模式、根是谁、方向、分组），
系统 Layout Engine 计算所有节点坐标——**模型不要输出精确 x/y 坐标**（写了也会被系统覆盖），
但必须分析清楚知识结构，否则布局引擎排出来也不会好看。

---

## JSON Canvas Schema（必须遵循）

根对象：

```json
{
  "layout": { "mode": "hierarchy", "root": "n1", "direction": "TB", "groups": [] },
  "nodes": [],
  "edges": []
}
```

### 布局（布局意图，可选；缺省按 hierarchy 布局）

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | ❌ | 布局算法版本（当前 1）；旧画布缺省视为 1 |
| `mode` | ✅ | `hierarchy`（层级，默认）/ `flow`（流程）/ `radial`（中心辐射）/ `grouped`（分组） |
| `root` | ❌ | 根节点 id（hierarchy/flow/radial 用）；缺省取 `isRoot:true` 节点或首个无入边节点 |
| `direction` | ❌ | `TB`（自上而下，默认）/ `LR`（自左向右，流程/时间演进用） |
| `main_path` | ❌ | 主流程/因果/时间链节点 id 数组（flow 模式；主链沿 direction 主轴排列，其余作分支） |
| `groups` | ❌ | 分组数组 `[{id, nodes:[...], title?}]`（grouped 模式必填） |

### Node

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 节点唯一标识，如 `n1`、`node-1` |
| `type` | ✅ | `text` / `file` / `image` / `link` / `url` / `bookmark` / `code` |
| `text` | 按类型 | text 节点内容（Markdown） |
| `file` | file 节点 | 知识库内真实相对路径（**绝不编造**，只来自 kb_search 或 read 到的文件） |
| `url` | link 节点 | http(s) 链接 |
| `code` | code 节点 | 代码片段 |
| `isRoot` | ❌ | 设为 `true` 标记唯一主题中心（最多一个） |
| `x/y/width/height` | ❌ | **不要填写**，由系统布局引擎计算并覆盖 |

### Edge

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ❌ | 可省略，系统自动补唯一 id |
| `fromNode` | ✅ | 必须指向存在的节点 id |
| `toNode` | ✅ | 必须指向存在的节点 id |
| `label` | ❌ | 关系说明（如"包含"、"依赖"） |

## Canvas 空间布局规范（v5）

> 位置 = 语义。空间结构必须表达知识结构，而不是装饰或随机摆放。
> 上/下 → 层级；左/右 → 流程/因果/演进；中心 → 核心；周围 → 从属；相邻 → 强相关；分区 → 不同领域。

### 一、布局决策流程（每次生成必须按序执行）

1. **确定主题中心/root**：存在明确中心则设 `isRoot: true`，最多一个。
2. **识别一级概念**：围绕中心的第一层子主题。
3. **识别二级/三级概念**：每个一级概念下的细分。
4. **分析关系类型**：层级 / 从属 / 流程 / 因果 / 依赖 / 时间演进 / 关联。
5. **选择布局模式**（见下）。
6. **建立空间层级**：在 layout 中声明 `root`、`direction`、必要时 `groups`。
7. **写 nodes/edges**：**不要写 x/y**（系统计算）。
8. **检查结构**：节点是否过多需分组、是否存在孤立/重复概念。
9. **写入 Canvas**：用 `write` 落盘，系统完成校验与布局。

### 二、布局模式选择

| 模式 | 适用 | layout 写法 |
|---|---|---|
| `hierarchy` | 概念树/分类/包含关系（JVM→内存/GC/调优） | `{"mode":"hierarchy","root":"n1"}`（TB） |
| `flow` | 流程/因果/时间演进（请求→检索→重排→生成）；存在明确主链时声明 `main_path` | `{"mode":"flow","root":"n1","direction":"LR","main_path":["n1","n2","n3"]}` |
| `radial` | 核心概念+从属（RAG 中心，检索/生成/数据环绕；一级 ≤8） | `{"mode":"radial","root":"n1"}` |
| `grouped` | 多领域分区（检索层/模型层/数据层各自成区） | `{"mode":"grouped","groups":[{"id":"g1","nodes":["n2","n3"]},...]}` |

**判断原则**：关系主要是「包含/分类」→ hierarchy；「先后/因果/时间」→ flow(LR)，
**且存在明确主流程/因果链/时间线时声明 `main_path`**（主链节点沿 direction 排列，
其余节点作为分支挂在最近主链祖先下）；「单一核心+多方向从属」→ radial；
「几个独立领域」→ grouped。

### 三、空间语义优先级

**语义关系 > 可读性 > 紧凑性 > 美观。**
- **Edge = 语义真相，Layout = 空间提示**：节点之间的真实知识关系（父子/流程/依赖）
  必须通过 `edges` 表达；`layout.groups` 只描述空间分区（哪些节点形成独立区域），
  **绝不把分组当作第二套知识关系**——两套结构不一致时以 edges 为准，不要出现
  `edges: A→B` 而 `groups: A、C、D` 相互矛盾的情况。
- 强关系节点必须相邻（`A→B` 时 A、B 靠近）。
- 同组节点形成连续区域；不同组之间保持明显间距（系统默认组间距 ≥160px）。
- 同一主关系链方向统一：`A→B→C→D` 不能忽左忽右、忽上忽下。
- root 位于视觉中心（radial）或顶部起点（hierarchy/flow）。
- **布局必须可重复**：同一知识结构应尽量保持稳定布局，不要为美观随机改变节点位置
  （系统布局是确定性的；模型只需保证 edges/layout 声明一致）。

### 四、节点密度控制

- 小主题：6~15 节点；中等：10~25；复杂：20~40。
- **节点过多时优先分组，不要平铺**：用 `grouped` 模式或 hierarchy 下加中间层级。
- 超过 40 个节点应拆成多个画布或明确分层（系统不阻止，但可读性差）。
- **radial 模式一级节点 ≤ 8**：超过时系统自动降级为 hierarchy，请优先规划好一级概念数量。

### 五、结构自检（写入前检查）

- ✅ 有明确中心/root？
- ✅ 一级概念围绕中心或形成层级？
- ✅ 流程/因果方向统一？
- ✅ 同组节点相邻、组间有间隔？
- ✅ 没有孤立无意义节点？
- ✅ 概念层级正确（父→子、整体→部分）？
- ✅ 没有把 30+ 节点平铺成一个平面？
- ❌ 不输出 x/y（交给系统）。

## 工作流

### 创建 Canvas
1. 理解用户主题；结合知识库时先用 `kb_search` 检索真实资料。
2. 按「布局决策流程」分析知识结构 → 选布局模式 → 设计 nodes/edges。
3. 生成完整 JSON（含 `layout` 意图；不含坐标）。
4. 用 `write` 写入 `xxx.canvas`（建议 `canvas/` 目录）；系统自动校验 + 布局。
5. 告知用户画布路径，说明"已可用 Canvas 页面打开查看"。

### 整理 Canvas
1. 用 `read` 读取 `.canvas`。
2. 分析节点/边/知识结构：删除无意义/孤立节点、合并重复概念、补充缺失关系、**重新评估布局模式**（必要时改 layout 字段）。
3. 保留真实 `file` 路径；可再 `kb_search` 补资料。
4. 重新生成完整 JSON（含 layout 意图）。
5. 用 `write` 覆盖原文件；覆盖前说明改动，如有疑虑先征询用户。

### 回答画布相关问题
1. 用 `read` 读取 `.canvas`，理解后回答；不凭记忆编造。

## 边界与安全

- `write` 覆盖已有画布前确认用户意图（不可撤销）。
- `file` 节点只能引用真实存在的相对路径，**禁止编造**。
- 不修改 `.mdgo` 受控数据。
- 不调用任何 Canvas 专用 Function（read_canvas / canvas_generate / canvas_organize 已不存在）。
