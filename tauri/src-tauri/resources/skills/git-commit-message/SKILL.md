# Git 提交信息生成

## 何时使用
- 暂存区（git index）已有改动，需要生成符合规范的提交信息
- 用户要求「写提交信息 / 生成 commit message / 总结本次改动」

## 何时不要用
- 暂存区为空：先暂存文件，不要凭空生成
- 用户要求直接提交：本技能只生成信息，不执行 `git commit`

## 输入
调用方会提供，缺项按缺失处理，不得猜测：
1. 当前分支名
2. 暂存文件列表：状态（A/M/D/R/C）、路径、+/− 行数
3. 暂存区 diff（可能被截断，截断处有标记）

本技能不依赖历史提交，不要假设或引用仓库既往提交信息。

## 工作流程
1. 通读文件列表与 diff，判断主要意图：新增功能 / 修复缺陷 / 纯文档 / 格式或重构 / 性能 / 测试 / 杂项
2. 选 `type`（见规范），选 `scope`（主要改动所属模块或目录名，小写；不确定则省略）
3. 写 `subject`：动宾结构、说明「做了什么」，不写空泛描述
4. 判断是否需要 `body`：动机、影响面、兼容性、注意事项；不需要则留空
5. 只有输入中明确出现 issue 或 breaking change 时才写 `footer`，否则留空
6. 按「输出格式」输出 JSON，并按「自检清单」逐条检查

## 聊天场景执行步骤
在对话中执行本技能时：
1. 先调用 `git_status` 确认存在已暂存文件；没有则直接说明「暂存区为空」，不要生成
2. 再调用 `git_diff`，参数 `staged=true`、`stat_only=false` 取暂存区差异
3. 仍按「输出格式」输出 JSON，方便用户直接取用

## 提交信息规范
### 格式
```
<type>(<scope>): <subject>

<body>

<footer>
```
- Header 必需；body、footer 可选
- Header 整行不得超过 70 个字符；第二行必须为空；body/footer 每行不超过 80 个字符
- `type` 与 `scope` 一律小写

### type（仅限以下取值）
| type | 含义 |
|---|---|
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 仅文档变更 |
| style | 不影响代码运行的格式变更（空白、缩进、分号等） |
| refactor | 重构（既非新功能也非修缺陷） |
| perf | 性能或体验优化 |
| test | 新增或修改测试 |
| chore | 构建过程、辅助工具、依赖等杂项 |
| revert | 回滚历史提交（body 注明被回滚的 commit） |

自动生成仅允许上表取值；不采用 Conventional Commits 的 `build`/`ci` 等扩展类型。
`to`、`merge`、`sync` 属人工场景（只出 diff / 代码合并 / 同步主线），不得使用。

### scope（可选）
- 取本次改动主要影响范围：模块名、目录名或组件名，小写
- 嵌套用 `/`（如 `agent/loop`），多模块用 `,` 分隔且不加空格
- 无法概括时直接省略括号，不要为凑 scope 编造名称

### subject
- 动宾结构、一般现在时、祈使句，不加主语；句尾不加句号
- 中文按字符计建议 ≤ 50，整个 header 硬上限 70
- 一个提交只表达一件事；禁止「更新代码」「修复问题」这类无实际意义的描述
- 使用英文时首字母小写

### body（可选）
- 说明「为什么改、影响面、注意事项」，不复述 diff、不贴代码
- 每行 ≤ 80 字符，建议不超过 5 行

### footer（可选）
- 仅写 `BREAKING CHANGE` 说明或关联 issue（如 `Closes #12`）
- 输入中没有明确信息时必须为空，禁止编造 issue 编号、链接、协作者

## 输出格式
只输出一个 JSON 对象，不要代码块、不要解释、不要多余文字：

```json
{
  "subject": "type(scope): 做了什么",
  "body": "可选正文，多行用 \\n 分隔；没有则空字符串",
  "footer": "可选；没有则空字符串",
  "notes": "给用户看的提示（如建议拆分提交），不会写入提交信息；没有则空字符串"
}
```

- `subject` 必须是完整 header（含 type 与冒号），不与 body 重复
- 所有键都必须出现，缺省用空字符串
- JSON 必须可被标准解析器解析：双引号、无尾逗号、无注释

## 硬性约束
1. 语言默认中文；仅当输入明确要求英文时使用英文，同一提交内不混用
2. 不编造：issue、PR、作者、未在输入中出现的改动
3. 不夸大：格式改动不得写成 feat，局部修改不得写成「重构整个模块」
4. diff 被截断时只概括可见部分，不推测截断内容
5. 不输出 emoji、不输出 changelog、不输出多个候选方案
6. 暂存内容明显是互不相关的多类改动时，按主要意图生成，并在 `notes` 提示「建议拆分提交」

## 示例

### 示例 1：新功能 + scope
输入：新增 `commands/git_ai.rs`，实现提交信息生成命令与单测
输出：`{"subject":"feat(git): 新增提交信息自动生成命令","body":"复用 skill 正文作为提示词，单次调用返回 subject/body；补充解析与预算裁剪单测。","footer":"","notes":""}`

### 示例 2：修缺陷，无 scope
输入：修复暂存列表在重命名文件时新旧路径颠倒
输出：`{"subject":"fix: 修正重命名文件状态解析顺序","body":"按 git status -z 的实际顺序解析 new/old，避免放弃更改作用到错误路径。","footer":"","notes":""}`

### 示例 3：纯文档
输入：更新 README 安装步骤与截图
输出：`{"subject":"docs: 更新安装步骤与截图","body":"","footer":"","notes":""}`

### 示例 4：改动过杂
输入：同时修改登录逻辑、调整 6 个文件缩进、更新 CI
输出：`{"subject":"fix(auth): 修复登录态刷新失败","body":"登录态过期后刷新请求未携带凭证，导致静默失败。","footer":"","notes":"本次暂存包含格式与 CI 改动，建议拆分为独立提交。"}`

## 自检清单
- [ ] subject 为 `type(scope): 描述` 形式，type 在允许列表内
- [ ] header ≤ 70 字符；subject 无句号、无空泛描述
- [ ] body 每行 ≤ 80 字符，未复述 diff
- [ ] footer 未编造 issue/链接（无信息时为空）
- [ ] 只输出一个 JSON 对象，无代码块与解释
- [ ] 语言为中文（除输入明确要求英文）

## 失败与降级
- 暂存区为空：输出 `{"subject":"","body":"","footer":"","notes":"暂存区为空，请先暂存文件"}`，不要生成信息
- 暂存内容全为二进制：输出 `{"subject":"chore: 更新二进制资源","body":"","footer":"","notes":"暂存内容为二进制，建议人工确认提交信息"}`
- 信息不足以判断意图：`type` 用 `chore`，只描述可见文件范围，不编造动机
